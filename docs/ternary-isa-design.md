# ternary-isa-design

# TriRV——基于 RISC-V 哲学的原生三进制 ISA 设计

> 目标：在 45-trit 字长（9 tryte）、非平衡三进制（0/1/2）的原生 VM 上，定义一套类 RISC-V 的精简指令集。
> 命名：**TriRV**（Ternary RISC-V），基础整数扩展记作 **TI**（对应 RV32I 的 I）。

---

## 0. 从 RISC-V 继承什么（设计哲学）

RISC-V RV32I 的四条核心智慧，全部保留：

| RISC-V 原则 | TriRV 对应做法 |
| --- | --- |
| Load-Store 架构 | 只有 load/store 访存，ALU 只操作寄存器 |
| 固定指令长度（32 bit） | 固定 **20 trit（4 tryte）** |
| 寄存器字段位置在所有格式中固定 | rd / rs1 / funct / opcode 位置全格式一致 |
| 立即数符号位固定在最高位，便于并行符号扩展 | 立即数符号 trit 固定在指令最高 trit `t19` |
| 32 个通用寄存器，x0 硬连 0 | 32 个 45-trit 寄存器，x0 硬连 0（编号对齐 x0–x31） |
| 模块化扩展（I/M/A/F/C） | TI / TM / TA / TT（三值逻辑）/ TC（压缩） |

**编码差异**：RISC-V 用 5 bit 编码 32 个寄存器；三进制用 4 trit（$3^4=81$）编码同样的 32 个，
余下 49 码留作将来扩展。选择 4 trit 而非 3 trit（27 个），是为了与 RISC-V 的 x0–x31 逐一对应，
见 §9-D3。

## 1. 数据表示

| 项 | 定义 |
| --- | --- |
| 基数 | 非平衡三进制，trit ∈ {0,1,2} |
| tryte | 5 trit（$3^5=243$），物理存 1 字节（方案 C 打包，见 ABI 文档） |
| 字（word） | 45 trit = 9 tryte（寄存器宽度） |
| 无符号值 | $\sum d_i 3^i,\ d_i\in\{0,1,2\}$，范围 $0..3^{45}-1$ |
| 有符号值 | **3 的补码**：$-x \equiv 3^{45}-x$；范围 $\approx \pm1.48\times10^{21}$ |
| 地址 | 按 byte（tryte）编址，与 ABI 一致 |
| 立即数符号 | 最高 trit = 2 表示负（3 的补码延伸） |

> ⚠️ 非平衡三进制的 3 补码**没有干净的符号位**（正负数分界不在单一 trit 上），这与 RISC-V 二进制补码不同。符号扩展规则必须显式定义，见 §9-D2。

### 1.1 度量口径（哪些是定义，哪些才是成本）

三进制与二进制的规格差异**不是缺陷，是定义**。本项目所有取舍按下表分账，不得混谈：

| 账本 | 内容 | 判定方式 |
| --- | --- | --- |
| **定义层** | 基数、trit 数、值域、地址单位、指令字宽 | **不作优劣比较**。宽度可自由定义，值域不够加 trit 即可；"能装多大的数"推不出任何工程结论 |
| **语义层** | RV32I 指令语义、ABI、C 语义、异常/CSR 行为 | **必须一致**，由差分测试判定 |
| **实现层** | 静态指令数、动态步数、墙钟、单步成本 | **必须实测**，只认可复现数字 |

由这条口径直接得到两个结论：

- **$2^{32}$ 不是 3 的幂，所以任何三进制字宽都无法无损表示 i32 全域。** 这既不是
  "$243^4 < 2^{32}$ 吃亏"，也不是"45 trit 装得下 i64 占便宜"——两侧都只是定义选择，
  不能记成收益或亏损。
- 成本只有一种形态：**模拟外来二进制语义所需的额外指令**（mod $2^{32}$ 规整、
  base-243 打包、8-bit 位运算展开）。它按**指令条数**计量，不按位宽计量。
  反向亦然：二进制机器模拟三进制语义要付 base-243 打包税（实测 60.8ns vs 1.62ns）。

### 1.2 执行载体：软核到底跑在什么上面

"ISA 是纯三进制的"和"VM 跑在二进制 CPU 上"**不矛盾**，但必须分成三层说，
否则会陷入"用二进制电脑写三进制模拟器，所以不算三进制"的循环否定——
按这个逻辑，所有 RISC-V 模拟器也都不算 RISC-V。

| 层 | 是什么 | 今天的状态 | 判断标准 |
| --- | --- | --- | --- |
| **ISA 语义层** | 每条指令对操作数做了什么、结果怎么解释 | **纯三进制**（见下表审计） | 语义定义不得引用"二进制位"这一概念 |
| **执行载体层** | 谁来取指、译码、算、写回 | 软件 VM（C / Python），宿主是 x86/ARM | **必然有宿主**。这是"第一步先做软核"的定义，不是缺陷 |
| **物理实现层** | 真芯片的三值电路（multivalued logic） | 未做 | 本层不在当前范围 |

**指令是怎么跑起来的**（以 C VM 为例，`trirv_vm.c`）：

```
1. 取指    fp 处取 4 个 tryte → 每个 tryte 是 0..242 的整数 → 合成 20 trit 指令字
2. 译码    按 t19..t0 切字段（opcode 3 / rd 4 / funct 2 / rs1 4 / rs2 4 / funct2 3）
3. 执行    按 opcode 分派；寄存器值存放在 __uint128_t 里，取值 mod 3^45
4. 写回    rd 取 (结果 mod 3^45)
```

第 3 步里，`__uint128_t` 是**载体的容器**——宿主只有二进制整数类型，
所以用 128 位二进制整数装一个 $0..3^{45}-1$ 的三进制数值。
容器是二进制的，**数值不是**：所有进出容器的运算都按 3 的幂定义
（`divmod243` 拆 tryte、`p *= 243` 拼回、`MOD = 3^45` 取模）。
容器换成三值电路，这套语义一个字都不用改。

#### 1.2.1 执行层与表示层（记数法正交维度，2026-11-20）

上面三层说的是"ISA 语义 / 谁执行 / 物理实现"。还有一个**正交维度**必须分清：
**执行层（硬件实际运算）**与**表示层（人看的记数法）**是两回事，不得互相冒充。

| 世界 | 执行层（硬件运算） | 表示层（记数法） |
| --- | --- | --- |
| 二进制 | 二进制门电路算 `10+10` | 十进制：`20` 只是记号，CPU 里没有十进制电路 |
| 三进制（TriRV） | 三进制门电路做三进制运算 | **十二进制**（`trirv_base12.py`），十进制是借用二进制世界的记法 |

- **CPU 没有十进制电路**：`10+10=20` 那串字符是表示层记号，底层全是二进制门在做加法。
  同理 TriRV 的执行层只有三进制，十二进制只是给人看/输入的记数法。
- **为什么表示层选 12**：`12 % 3 == 0`、`10 % 3 == 1`（实测）。二进制世界用十进制记数
  是历史习惯；三进制世界用十二进制更契合——`1/3 = 0.4` 是十二进制有限位，
  十进制 `1/3 = 0.333…` 无限，而三进制硬件天然做三等分。
- **度量口径**：精度/数值的执行层度量是 **trit**。"十进制有效位""十二进制位"都是
  表示层换算（1 trit ≈ 0.442 十二进制位），不进入 ISA 定义。
- **数码与进制标注（2026-11-20）**："12" 是十进制进位写法（`1×10+2`），十二进制自己的
  基数写作 `10`（`1×12+0`），字样 `12` 在十二进制里 = 十进制 14。表示层必须显式定义
  数码（`SYMBOL_SET`，用户拍板暂用 ASCII `0-9AB`，字形约定非数学定义）与标注法：
  **数字加下标**标明基数，如 `18₁₂`（十进制 20）、`20₁₀`；下标是元层注解，不属于数值。
- 工具：`trirv_base12.py` 提供 `to12`/`from12`/`frac_to12`/`labelled`/`parse_labelled`
  （72 项契约测试），仅做表示层记数转换，不改任何执行层数值。

**语义层审计（2026-11-19，全指令逐条核对）**：

| 指令组 | 语义定义 | 依赖二进制？ |
| --- | --- | --- |
| `ADD/SUB/ADDI` | 整数加减，对 $3^{45}$ 取模 | ❌ 无关 |
| `MUL` / `MULH` | 低半 / $\lfloor ab/3^{45}\rfloor$ 高半，按 tryte 卷积进位实现 | ❌ 无关（`mul90` 全程 `%243` `/243`，无 `<<`） |
| `DIV/REM/DIVU/REMU` | 向零截断 / 余数；无符号 = 按非平衡读法 $0..3^{45}-1$ | ❌ 无关（平衡/非平衡是三进制的两种读法，不是"符号位"） |
| `AND/OR/XOR` + `I` 形式 | 逐 trit `min` / `max` / `(a+b) mod 3` | ❌ 无关（2026-11-19 起，见 §5.1） |
| `TMIN/TMAX/TNOT/TAND/TOR` | 逐 trit 三值逻辑 | ❌ 无关 |
| `SLL/SRL/SRA` + `I` 形式 | $\times 3^{k}$ / $\lfloor \cdot /3^{k}\rfloor$，移位量取低 7 trit（$3^7$） | ❌ 无关（对应 RV32 的 shamt 取低 5 bit） |
| `SLT/SLTU/BLT/BGEU` 等 | 有符号 = 平衡读法，无符号 = 非平衡读法 | ❌ 无关 |
| `LB/LH/LBU/LHU` | 1/2 tryte 的符号/零扩展（阈值 121 / 29524） | ❌ 无关 |
| `LW/SW/SB/SH` | 9 / 1 / 2 tryte 存取，按 243 的幂拼接 | ❌ 无关 |

**结论：语义层已无二进制依赖。** 曾经有过的唯一一处是 `AND/OR/XOR`
直接调宿主 `& | ^`（等于借宿主的二进制 ALU），已于 §5.1 改为逐 trit。

**性能口径（重要）**：测成本必须用 **C VM**（`./trirv_vm`）。
Python VM 单条指令 ~76 ns 是解释器开销（大整数运算 + 属性查找），
不代表架构成本，**只用于语义差分，不用于测性能**。

而 C VM 的数字也只能在"同一宿主上比较优化"，不能论证架构成本 ——
它在乘法与除法上受宿主硬件乘法器/除法器加速，严重低估真实数据通路的代价。
这一点由 §1.3 的 tryte 数组参考实现给出定量证据。

> 早期用 200 万次循环测得 `ADD 1.88ns / MUL 1.88ns`，已被判定为**测量污染**
> （3–4ms 的总耗时里，进程启动占了大头，MUL 与 ADD 同值就是信号）。
> 正确做法是 2000 万次循环并扣基线，见 §1.3 的对照表。


### 1.3 trit 级成本模型（tryte 数组参考实现）

§1.2 的结论只解决了"语义干净"，没解决"成本画像"。因为 `__uint128_t` 是
**二进制容器**，它自带两件宿主特权，会让成本严重失真：

- **硬件除法器**：`a / b` 是一条 CPU 指令（~20–40 周期），而三进制数据通路没这东西
- **硬件乘法器**：`a * b` 是一条指令（~3 周期），三进制要 tryte 卷积 + 进位

所以 `trirv_tritref.py` 换掉容器：**一个 45-trit 值 = 9 个 tryte 的数组**（每个 0..242），
所有运算只走 tryte 级原语（加 / 减 / 比较 / 查表 / 移位 / 卷积），并统计原语调用次数。
这个计数**与宿主无关**，可以直接拿去对照硬件数据通路。

**语义等价性**：与二进制容器逐例差分 **46164 项，0 失败**（含除法三种基数）；端到端用 tryte 原语
直接算 `Σ1..1000 = 500500`、`fib(21) = 10946`、`20! mod 3^45` 全对。

**每条 ISA 操作的 trit 级代价**（1 tryte 原语 = 一次 5-trit 加/减/比较/查表；主列 45-trit 全宽）：

| ISA 操作 | 全宽 | 4 tryte | 相对 ADD | 构成 |
| --- | --- | --- | --- | --- |
| `ADD` / `SUB` | 9 | 9 | 1.0× | 9 次 tryte 加 + 进位 |
| `SLT` / `SLTU`（典型） | 4 | 11 | 0.4× | 判号命中 + 高位优先比较，提前退出 |
| `SLT` / `SLTU`（最坏：值 ≈ HALF） | 48 | 48 | 5.3× | 符号扫描 45 trit |
| `AND` / `OR` / `XOR` | 45 | 45 | 5.0× | 逐 trit 查表（9 tryte × 5 trit） |
| `SLL` / `SRL` k=1 | 9 | 9 | 1.0× | tryte 内乘 3，无搬移 |
| `SLL` / `SRL` k=13 | 34 | 34 | 3.8× | 2 tryte 搬移 + 乘/除 3³ |
| `MUL`（低半）/ `MULH` | 99 | 27 | 11.0× | tryte 卷积 9×9 + 进位传播 |
| `LW` + `SW` 往返 | 18 | 18 | 2.0× | 按 243 的幂拼接，无字节移位 |
| `LB`（`LBU` 免费） | 1 | 1 | 0.1× | 阈值 121 判号 |
| **`DIVU`（全宽 / 全宽）** | **711** | — | **79×** | 15 轮基数 27 |
| `DIVU`（全宽 / 4 tryte） | 442 | — | 49× | 15 轮基数 27 |

两点读数：

- **`MUL` 的真实成本是 11×，不是早先写的 3.3×。** 那张表用 `12345678` 这类 4-tryte
  操作数统计，把 4-tryte 的 27 当成了全宽成本。硬件关键路径按 45 trit 算，卷积是 81 次。
- **`SLT` 存在 12 倍的典型/最坏差**（4 对 48）。这是"没有符号位"的直接代价：
  值接近 `HALF = 111…1` 时要扫满 45 个 trit 才能判号。二进制 `SLT` 是"符号位异或
  + 无符号比较"，恒定代价。

**除法器：三处去浪费 + 一次基数扫描**

原实现 1640 的问题不在算法，在三处浪费：余量宽度固定 10 tryte（除数只有 1 tryte
时也跑满进位链）、45 轮从第 44 位空转到第 0 位（不看被除数实际宽度）、每轮只吞
1 个 trit（商位逐个试）。改后 `divmod_radix`：

| m（trit/轮） | 基数 | 轮数 | 除数全宽 | 除数 4 tryte |
| --- | --- | --- | --- | --- |
| 1 | 3 | 45 | 1071 | 624 |
| 2 | 9 | 23 | 715 | 456 |
| 3 | 27 | 15 | 711 | 442 |

**m=2 与 m=3 打平（715 vs 711）**，基数再高也不省：每轮的全宽加/减/移位是 ~3m 个
tryte 操作，而倍数表要 (3^m − 1) 个 tryte 加 —— 表成本随基数指数涨、轮数线性降，
最优点在 m≈2~3。**这是硬件结论**：三进制除法的瓶颈是每轮的整字加减，不是轮数。

成本随除数宽度增长（被除数全宽，m=3，除数取该宽度最密值）：1 tryte 289 → 4 tryte 442
→ 9 tryte 719，近似线性（每加 1 tryte 约 +50），因为宽度直接决定进位链长度。硬件先做前导零检测
再决定数据通路宽度，正是这个原因。

**撤回上一轮的一个错误结论**

上一轮写过"C VM 上 `DIV` 只比 `MUL` 贵 2.7 倍，按 tryte 原语算是 55 倍，差额来自
宿主有硬件除法器"。**这个 55 倍是假的**：模型用的是 45-trit 全宽操作数，而 VM 基准
用的是 `12 / 10`。同宽重算（都用 `12` 和 `10`）：

| 操作 | tryte 原语 | C VM 净增量 |
| --- | --- | --- |
| `ADD` | 9 | 0（基线） |
| `MUL` | 19 | +43.1 ns |
| `AND` | 45 | +36.5 ns |
| `DIV` | 95 | +115.7 ns |

`DIV`/`MUL`：模型 5.0×，VM 2.7× —— **同量级**。原因是 `__uint128_t` 的除法在 x86 上
本来就是库函数做的二进制长除（约 128 轮），结构与三进制逐位试商同类，所以两边吻合。
把不同宽度的两个数摆在一起比，得到的不是架构差异，是口径错误。

修正后的口径：

- VM 的**绝对墙钟**不代表硬件周期：硬件 `ADD` 是 9 个 tryte 的串行进位，
  VM 的 `ADD` 是一条 128 位指令，两者不可比。
- VM 的**相对成本**与模型同量级，可用于同一宿主上的优化比较（如栈到寄存器 9.4× 降到 1.5×），
  但精度不够，不能当架构结论。
- 模型独有的价值是**随宽度变化的规律**：VM 的二进制运算宽度无关，模型的成本随 tryte 数涨。

**两个踩坑（都是"看起来更三进制，其实错"）**：

1. **判号不能用最高 trit**。3 补码分界点是 `111…1 | 111…2`，
   `HALF = (3^45-1)/2` 本身就落在全 1 上，所以**不存在单一符号位**。
   正确判据：从高位往下找**第一个不是 1 的 trit**，是 2 则为负。写错时 4372/43456 例出错。
2. **逐 tryte 平衡比较也是错的**。非平衡表示的位置权重是 243^i，
   9 个 tryte 各自按 [-121..121] 平衡解释**并不等于**整体值平衡。
   `SLT` 只能先判号、同号再按非平衡顺序比。

## 2. 指令格式（6 种，对齐 RISC-V R/I/S/B/U/J）

### 2.1 字段位置（t19 最高位 … t0 最低位，共 20 trit）

| 字段 | 位置 | 宽度 | 编码容量 | 说明 |
| --- | --- | --- | --- | --- |
| opcode | t2..t0 | 3 trit | 27 | 指令大类 |
| rd | t6..t3 | 4 trit | 81（用 32） | 目标寄存器 |
| funct | t8..t7 | 2 trit | 9 | 子功能（等价 funct3） |
| rs1 | t12..t9 | 4 trit | 81（用 32） | 源寄存器 1 |
| rs2 | t16..t13 | 4 trit | 81（用 32） | 源寄存器 2 |
| funct2 / imm | t19..t17 | 3 trit | 27 | 扩展功能或立即数高位 |

> **D3（2026-11-19 撤销 27 方案）**：rd/rs1/rs2 保持 4-trit（32 个寄存器），
> 吃掉原先空闲的 t6/t12/t16 三个 trit——20 trit 恰好用满：3+4+2+4+4+3 = 20。
> 立即数布局完全不变——I 型仍占 t19..t13，S/B 型仍占 t19..t17 + t6..t3，
> U/J 型仍占 t19..t7，故汇编器标签差值与编译器跳转零改动。

> 与 RISC-V 一样：**rd、funct、rs1、rs2、opcode 在所有格式中位置固定**，解码器可并行读寄存器。

### 2.2 六种格式布局

```
R-type (寄存器-寄存器 ALU):
  t19..t17 | t16..t13 | t12..t9 | t8..t7 | t6..t3 | t2..t0
  funct2   |   rs2    |   rs1   | funct  |   rd   | opcode
  (20 trit 全部用满，无空闲位)

I-type (立即数 / load / jalr):
  t19..t13 (7 trit)   | t12..t9 | t8..t7 | t6..t3 | t2..t0
  imm[6:0]            |   rs1   | funct  |   rd   | opcode
  (imm 占 t13..t19 = rs2 位置 4 trit + funct2 位置 3 trit)

S-type (store):
  t19..t17 | t16..t13 | t12..t9 | t8..t7 | t6..t3  | t2..t0
  imm[6:4] |   rs2    |   rs1   | funct  | imm[3:0]| opcode
  (低段 imm 复用 rd 字段位置——S 型无 rd)

B-type (分支，立即数打乱以固定 rs 位置):
  t19..t17 | t16..t13 | t12..t9 | t8..t7 | t6..t3        | t2..t0
  imm[6|4:1] |  rs2   |   rs1   | funct  | imm[5|3:0]    | opcode
  (rs2/rs1 同 S-type；低段 imm 复用 rd 位置)

U-type (lui / auipc):
  t19..t7 (13 trit)   | t6..t3 | t2..t0
  imm[12:0]           |   rd   | opcode

J-type (jal):
  t19..t7 (13 trit)   | t6..t3 | t2..t0
  imm[12:0]           |   rd   | opcode
```

**立即数宽度**：I/S/B 为 7 trit（$3^7=2187\approx2^{11}$）；U/J 为 13 trit（$3^{13}\approx2^{20.6}$）。

## 4. 基础整数指令集 TI（对应 RV32I 的 40 条）

### 4.1 ALU（R-type，opcode=0）

`ADD, SUB, SLL, SLT, SLTU, XOR, SRL, SRA, OR, AND, TMIN, TMAX`（后两条属 TT 扩展）

### 4.2 ALU 立即数（I-type，opcode=1）

`ADDI, SLTI, SLTIU, XORI, ORI, ANDI, SLLI, SRLI, SRAI`

### 4.3 Load（I-type，opcode=2）

`LB, LH, LW, LBU, LHU, LW4` —— 按 tryte/2tryte/9tryte/4tryte 取数。

> **LW4（__tint2 档，2026-11-23 C2 方案 A 拍板）**：4 tryte = 20-trit 装载，
> 合成值按半阈值 `(3²⁰−1)/2 = 1743392200` 三补码符号扩展进 45-trit 寄存器
> （funct=5；LOAD funct 头寸 0..4 已用，5..8 空闲）。值域 3^20 ≈ 2^31.6
> = "32 位量级档"，对标 char/short/int 阶梯补档。

> **符号性约定（与 RISC-V 完全一致）**：`LB`/`LH` **符号扩展**，`LBU`/`LHU` **零扩展**。
> 5-trit tryte 的符号区间是 −121..121（半阈值 `(3⁵−1)/2 = 121`），
> 10-trit 半字是 −29524..29524（半阈值 `(3¹⁰−1)/2 = 29524`）。
>
> 至于 `char` 本身：**它是无符号的 0..242**，但这不是对 RISC-V 的偏离——RISC-V psABI
> 同样规定 plain `char` 无符号（GCC riscv 后端 `DEFAULT_SIGNED_CHAR = 0`），TriRV 的
> tryte 值域与之天然吻合。因此编译器对 `char`/`unsigned char` 发 `LBU`，
> 只有显式 `signed char` 才发 `LB`。`TSEXT` 因此退化为可选的便利指令（TT 扩展成员），
> 不再是 char 语义的必需品。

### 4.4 Store（S-type，opcode=3）

`SB, SH, SW, SW4` —— **SW4（__tint2 档，同上拍板）**：4 tryte 存储，
低 20-trit 截断（mod 3^20；funct=3；STORE funct 头寸 3..8 空闲）。

### 4.5 Branch（B-type，opcode=4）

`BEQ, BNE, BLT, BGE, BLTU, BGEU`

### 4.6 Jump（opcode=5/6）

`JAL`（J-type）、`JALR`（I-type）

### 4.7 高位立即数（U-type，opcode=7/8）

`LUI`（load upper immediate）、`AUIPC`（add upper immediate to PC）

### 4.8 系统（opcode=9）

`ECALL, EBREAK, FENCE`

## 5. 三值逻辑扩展 TT（TriRV 独有，这是亮点）

非平衡三进制的 0/1/2 天然支持**三值逻辑**，这是二进制 ISA 没有的能力。借鉴 Kleene 强三值逻辑（0=假, 2=真, 1=未知）：

| 指令 | 语义（逐 trit） | 逻辑含义 |
| --- | --- | --- |
| `TMIN` | $\min(a_i,b_i)$ | Kleene AND（假优先） |
| `TMAX` | $\max(a_i,b_i)$ | Kleene OR（真优先） |
| `TNOT` | $2-a_i$ | 逻辑非（0↔2, 1→1） |
| `TOR` | Kleene 或 | 见真值表 |
| `TAND` | Kleene 与 | 见真值表 |
| `TNEG` | 3 补码取负 | 算术求反 |
| `TPACK` | 5 trit → 1 byte | 方案 C 打包 |
| `TUNPACK` | 1 byte → 5 trit | 方案 C 解包 |
| `TSEXT` | 取 rs1 **低 5 trit（1 tryte）**按 3 补码符号扩展到 45 trit | 便利指令（`LB` 已能直接符号扩展）；保留供 TT 扩展与手工位操作使用 |

**Kleene 真值表**（AND = min, OR = max, NOT = 2−x）：

| a | b | TAND | TOR |
| --- | --- | --- | --- |
| 0 | 0 | 0 | 0 |
| 0 | 1 | 0 | 1 |
| 0 | 2 | 0 | 2 |
| 1 | 1 | 1 | 1 |
| 1 | 2 | 1 | 2 |
| 2 | 2 | 2 | 2 |

> 这些指令让 VM 能原生做不确定逻辑、三值神经网络激活、量化权重运算——正是你的 2bit/1trit 场景。

### 5.1 `AND / OR / XOR` 的进制归属（2026-11-19 决议 B，已实施）

**背景：代码曾经与本文档 §7 不一致，且两组指令处在两个进制坐标系里。**

实测（旧实现，`trirv_vm`）：

```
AND 12,10 = 8      OR 12,10 = 14     XOR 12,10 = 6      <- 二进制按位
SLLI 12,2 = 108 = 12×9                                  <- 三进制移位
C:  x=10 -> x<<1=30(×3), x&6=2(二进制), x>>1=3(÷3)      <- 同一个 C 程序里两个进制
```

`AND/OR/XOR` 走的是宿主的 `& | ^`，等于**借宿主的二进制 ALU 作弊**；
三进制硬件里没有二进制位，这条指令根本无法直接实现。

**决议：统一到三进制（方案 B）。**

| 指令 | 语义（逐 trit） | 同义指令 |
| --- | --- | --- |
| `AND` / `ANDI` | $\min(a_i,b_i)$ | ≡ `TAND` / `TMIN` |
| `OR` / `ORI` | $\max(a_i,b_i)$ | ≡ `TOR` / `TMAX` |
| `XOR` / `XORI` | $(a_i+b_i)\bmod 3$ | —（三进制的"不进位加法"，二进制的自然类比） |
| `AMOAND` / `AMOOR` / `AMOXOR` | 同上，作用于内存旧值 | — |

**为什么保留 RISC-V 的名字**：`AND`/`OR` 是三值逻辑的 min/max，与 `TMIN`/`TMAX`
同义，等于给 RISC-V 兼容名和三值逻辑名各留一份；`XOR` 则是三进制唯一自然的
"按位可逆运算"。这样 §7「AND/OR/XOR → TMIN/TMAX/TNOT」的意图就落到了代码里。

**连带改动（必须做，否则静默错码）：**

1. `XORI x, 1` 曾遍布两套编译器当作**逻辑取反**（x∈{0,1}）。三进制下
   $1+1=2 \ne 0$，取反立刻失效。全部换成 `SLTU rd, zero, rs`（= `rs != 0`）
   或 `SLTIU rd, rs, 1`（= `rs == 0`）。
2. C 的 `& | ^` 要的是**二进制**语义，三进制 ISA 给不了。两套编译器现在
   **硬报错**而不是静默映射：
   `UNSUPPORTED: 二进制位运算 & —— 三进制 ISA 的 AND/OR/XOR 是逐 trit 三值逻辑…`
   真要支持，只能走软件模拟（45-trit 值的二进制展开 + 位走查，
   与 wasm 的 `i32.and` 同法，实测 372–436 条指令/次）。**尚未实现。**
3. C 的 `<<`/`>>` 保持三进制（×3^k / ÷3^k）。这意味 C 在 TriRV 上是
   "三值 C"而非 ISO C —— 与 `int` 只有 45 trit 而非 32 bit 属同一类偏离。

**怎么验证**：`trirv_tritlogic_e2e.py` 锁定语义（42 组三方差分：Python 期望值 ×
PyVM × C VM）；`trirv_fuzz.py` 的 1500 例随机指令池含 `AND/OR/XOR` 与
`ANDI/ORI/XORI`，两套 VM 字节级 MATCH。

> 教训：这条指令曾经在两套 VM 里各有一份实现（switch 分派 + 计算 goto），
> 只改一处时立即数形式仍是二进制 —— 差分测试把这种"改一半"抓了出来。

#### 5.1.1 边界：二进制位运算属于"外来语义适配层"，不进 ISA

> **废案条款（2026-11-22，用户拍板）**：本节设计的「方案 A」软件适配层已**整体
> 退役**——C 方言本身定义为**三值本征**，不再向 ISO C 二进制语义妥协：
>
> | C 运算符 | 本征语义 | 指令 |
> |---|---|---|
> | `a & b` | 逐 trit min | TAND |
> | `a \| b` | 逐 trit max | TOR |
> | `a ^ b` | 逐 trit (ta+tb) mod 3（不自反：a^a≠0） | XOR |
> | `~a` | 逐 trit 2−t（≡ −1−a；~0 = −1） | TNOT |
> | `a << k` | ×3^k mod 3^45 | SLL/SLLI |
> | `a >> k` | ÷3^k 向零截断（≡ 除法；无符号 raw ÷3^k） | SRA/SRAI、SRL/SRLI |
>
> 各 1 条指令、零工作寄存器（方案 A 每次位运算 ~753 条动态指令 + 抢占
> 5-7 个 callee-saved）。二进制兼容（白名单/接口）属后期另行立项。
> 本节以下内容保留为历史设计记录；当前口径以
> `tests/trirv_bitview_e2e.py`（245 项）与 `tests/trirv_tritlogic_e2e.py`
> （106 项 ISA 锚）为权威锁定。

既然 ISA 是纯三进制的，**"第 k 个二进制位"在 ISA 里没有位置**——它是二进制
的坐标概念，三进制寄存器里只有 trit。所以分层必须是：

```
┌─ 外来语义适配层 ────────────────────────────┐
│  wasm i32.and/shl/rot/clz  ·  C 的 & | ^ << >>  │  ← 用三进制指令"模拟"二进制语义
│  代价：32 轮无除法拆位，372–436 条指令/次        │     贵，但只对外来程序收费
└─────────────────────────────────────────────┘
┌─ TriRV ISA（纯三进制）──────────────────────┐
│  只有 trit 级操作：min/max/mod-3 加、×3^k、逐 trit 逻辑 │
└─────────────────────────────────────────────┘
```

这直接决定了两件事：

1. **不做决议 C**（不在 TT 扩展里加"取第 k 个二进制位"指令）。加一条就多一条
   非 RISC-V 指令，偏离"只换进制、不另建生态"的定位；而不加，位运算只是**慢**，
   不是**做不到**。
2. **C 的 `& | ^ ~` 不做成"ISA 指令直译"**，而是软件模拟，与 wasm `i32.and`
   走同一条路。**2026-11-19 已实现（方案 A），语义如下**：

   | 项 | 定义 |
   | --- | --- |
   | `bits(x)` | 45-trit 字的**原始值**（0..3^45-1）。负数的原始值就是 `3^45-\|x\|`，与 `x+3^45` 恒等 |
   | 视图宽度 | **72 位**（最小 W 使 2^W > 3^45-1；2^71=2.36e21 < 3^45=2.95e21 < 2^72） |
   | 回绕 | **在 3^45**，不是 2^k |
   | 结果 | 就是 45-trit 字本身，无需"映回" |

   **实现上最省的一点**：45-trit 寄存器的 raw 值**天然就是位模式**，所以既不用
   "无符号化"也不用"映回"，全程在模 3^45 域里跑（`SUB`/`ADD` 天然回绕），
   只需把比较换成 `SLTU/SLTIU`、除法换成 `DIVU`。逐位走查用**递推权重**
   `p = 2^71, 2^70, …, 0`，`p` 归零即循环结束，省掉计数器。
   成本：**实测 753 条动态指令/次**（C VM 上 `a&b` 761 步 vs `a+b` 8 步，
   约 94 倍 `ADD`；约 10.5 条/轮 × 72 轮）。

   > **两个必须记住的坑**（都实际踩过）：
   > 1. `3^45` **装不进寄存器**——它就是模数，装进去等于 0。所以任何
   >    "`x + 3^45`"式的无符号化写法都会静默失效。`~a` 因而改写成
   >    `((2^72-1) mod 3^45) - a`，那个常量（1.77e21）是可表示的。
   > 2. `~0 ≠ -1`。72 位全取反后按 3^45 回绕得到 1.768e21，这是方案 A 的
   >    **定义后果**，不是 bug。依赖 `~0` 当全 1 掩码的代码在 TriRV 上不成立。

   **`<< >>` 也已落地（同日）。** 关键是不必"拆 72 位"——两个方向都有直接的算式：

   | 运算 | 定义 | 实现 | 实测步数（`a+b` = 8 为基准） |
   | --- | --- | --- | --- |
   | `x << k` | `bits(x)·2^k mod 3^45` | `ADD d,d,d` 重复 k 次（**ADD 天然按 3^45 回绕**，正好就是定义）；k > 10 换成一次 `MUL`（`2^k mod 3^45` 编译期算好） | `a<<1` **9**、`a<<20` **18** |
   | `x >> k`（无符号） | `bits(x) >> k` | 一次 `DIVU`（除法天然向下取整） | `a>>3` **19** |
   | `x >> k`（有符号） | `floor(x / 2^k)` | `DIV` 向零截断，负数且有余数时再减 1（`REM` 的符号就是判据） | `a>>3` **25** |
   | 变量移位量 | 同上 | 循环 k 次单步；需要 2 个 callee-saved 工作寄存器 | `a<<n` **45**、`a>>n` **65**（n=5） |

   与 `& | ^` 的 753 条相比，移位几乎不花钱——因为**移位的定义本身就在算术里**，
   只有按位逻辑才需要逐位走查。这是本 ISA 一条值得记住的分界：
   **算术闭合的二进制操作（乘 2^k、除 2^k）不需要适配层，逻辑操作才需要。**

   > **历史的坑**：早先编译器把 `<<` 直译成 ISA 的 `SLL`（三进制 ×3^k），
   > 于是 `x<<1` 静默变成 ×3——实测 `x=10` 返回 **30**，而 C 语义要求 **20**。
   > 错误存在很久没人发现，因为两边都"能跑出数"。现在 `trirv_tdd_contract.py`
   > §10.5 直接断言汇编里**不得出现 `SLL/SRL/SRA`**。

   > **边界的确定行为**（C 里都是 UB，这里给的是定义而非猜测，不静默）：
   > 编译期移位量为负或 > 4096 → 硬报错；运行时移位量 ≥ 72 无符号得 0、
   > 有符号 ≥ 71 得 `0 / -1`（因为 `|x| < 2^71 = 2.36e21`）；
   > 运行时负数移位量按 0 次处理（循环条件是 `cnt > 0`，不会挂死）。

   > **第三条坑（2026-11-19 由契约测试发现）：位运算在这套 ABI 下不是代数结构。**
   > 每次运算结果都要按 3^45 回绕，72 位视图**不闭合**，于是组合表达式依赖求值顺序：
   >
   > | 律 | 是否成立 | 实测（a=123456789, b=-987654321） |
   > | --- | --- | --- |
   > | 幂等 `a&a==a`、`a|a==a` | ✅ | |
   > | 零元 `a&0==0`、单位元 `a\|0==a` | ✅ | |
   > | 对合 `~~a==a`、交换 `a^b==b^a` | ✅ | |
   > | 德摩根 `~(a&b)==~a\|~b` | ❌ | 左 -1.186258930232e21，右 -1.186258930227e21 |
   > | 结合 `(a\|b)\|c==a\|(b\|c)` | ❌ | 差 2.0e13 |
   > | 分配 `a&(b\|c)==(a&b)\|(a&c)` | ❌ | 8.40e7 vs 1.06e8 |
   >
   > 原因只有一个：`~(a&b)` 里的取反发生在 **72 位上**，而 `~a` 这个中间结果已经被
   > 折回 45 trit（高位被丢掉），再参与的 OR 就少了那一截。**只有单次运算的语义
   > 是干净的**；多步位运算表达式请当作"每步都会截断"来理解。
   > `trirv_tdd_contract.py` §7.2 把这四条**不成立**的律也锁进了测试——将来若真有
   > 人改 ABI 让它们成立，测试会立刻报出来。

顺带一个三进制独有、二进制没有的自由：**同一组 trit 有两种合法读法**
（平衡 $-121..121$ / 非平衡 $0..242$），所以 `SLT`（有符号）与 `SLTU`（无符号）
在 VM 里只是同一个值换一种解释（`s()` / `u()`），**不需要额外指令、不需要移位**。
二进制的"无符号"要靠忽略符号位、`SLTU` 要单独一套比较逻辑；三进制这边是对称的。

## 7. 与 RISC-V 的逐项对应

| RISC-V | TriRV | 差异原因 |
| --- | --- | --- |
| 32-bit 指令 | 20-trit 指令 | $3^{20}\approx2^{31.7}$，编码密度对等 |
| 5-bit 寄存器字段（=32） | 4-trit 字段（=81，用 32） | 编号与别名保持 x0–x31 一致，余码留扩展 |
| 12-bit 立即数 | 7-trit 立即数 | $3^7\approx2^{11}$，略小但同量级 |
| 二进制补码 | 3 的补码 | 基数变化 |
| AND/OR/XOR | TMIN/TMAX/TNOT + XOR | 三值逻辑更丰富 —— **已按此落地：AND=min、OR=max、XOR=逐 trit mod 3 加，见 §5.1** |
| 符号位在 bit31 | **没有单一符号位** | 3 补码正负分界落在 `111…1 \| 111…2`，`HALF` 本身就是全 1。判号要从高位往下找第一个 ≠1 的 trit，最坏扫 45 trit（§1.3 实测 `SLT` 最坏 48 原语 vs 典型 4）。这是三进制相对二进制的**真实**代价 |

> 这五项曾长期悬置。2026-11-18 首次拍板；**2026-11-19 按"以 RISC-V 为规范标准"的战略撤销 D3**

| 编号 | 决策点 | 拍板结论 | 被否决方案与否决理由 |
| --- | --- | --- | --- |
| **D1** | 指令字长 | **20 trit**（= 4 tryte 容量，恰好填满） | ~~21 trit~~：3²¹ ≈ 2³³·²⁸ 并非"精确 32-bit"；改 21 需 5 tryte 容器，PC 从 `4*i` 变 `5*i`，编码/跳转/对齐/全部 golden 失效。 |

| **D3** | 寄存器字段 | ✅ **已撤销 27 方案，回到 32 寄存器 / 4-trit 字段**（2026-11-19） | ~~27 寄存器 / 3-trit 字段~~（2026-11-18 曾实施，零浪费）：破坏 RISC-V x0–x31 ABI 与 LLVM 后端复用，与"以 RISC-V 为规范标准"的战略冲突。改回 4-trit 后 20 trit 恰好用满（原 t6/t12/t16 空闲位并入），立即数布局零改动，别名表恢复 RISC-V 标准编号。 |
| **D4** | 立即数位宽 | **I 型 7 trit / U 型 13 trit** | ~~加宽字段~~：大常数已由 `LUI+ADDI`（编译器 `load_imm` 用 3×15-trit 分段）覆盖全 45-trit 幅值并经全幅 fuzz 验证；加宽字段会重排全部编码格式。 |
| **D5** | 数据字长 | **45 trit = 9 tryte**（`long = pointer`，已同宽） | ~~40 trit~~：曾为迎合 LP64 试改，但**三进制硬件无 64 位概念**，LP64 是宿主二进制 ABI 惯例、不构成 TriRV 约束；45 trit 下 long=pointer 本就同宽。2026-11-18 短暂试改后**已撤回**，全链路恢复 45-trit，73/73 + 全 fuzz 绿。**更正**：PC 编址独立记 §11.3，D5 仅指数据字长。 |

### 11.1.1 指令级随机差分 fuzz 与 MUL 溢出修复（2026-11-18）

新增 `trirv_fuzz.py`：在一个程序里批量生成随机 ALU 操作，结果写入内存后由
`write` syscall 整块输出，Python VM 与 C VM 对比字节流，差异时逐 case 定位。
操作数池覆盖全 45-trit 范围（`±HALF_X`、`±3^44`、word 全 1/全 2、随机 word），
`emit_load()` 用 3×15-trit 分段装载任意 45-trit 常量。

- **发现的真 bug —— MUL 在 128 位上乘溢出**：`MUL(-3^44, HALF_X-1)` 的乘积
  ≈ `-1.45e42`，远超 `2^127≈1.7e38`。C VM 两处引擎的 `case OP_MUL` 原用
  `u(a*b)`，`__int128` 相乘溢出得到错误值（Python 大整数正确返回 0，因乘积恰为
  `3^45` 的倍数）。修法：两处均改用 `mul90()` 取低半 `lo=(a·b) mod 3^45`，
  与 MULH 系列共用 90-trit schoolbook 乘法，零溢出。
- **澄清**：此 bug 与"除法溢出"无关。TriRV 模 `3^45` 为奇数，3 补码范围对称
  `[-HALF_X, HALF_X]`，`MIN÷-1=MAX` 仍在范围内，不存在二进制补码 `INT_MIN/-1`
  那种溢出。`divmod_word()` 的"无除法器"指用逐位恢复除法实现（零硬件 `div`），
  是**实现手段**；此处 MUL 是**数值幅值超出 C 宿主类型**（`__int128`），二者正交。

验证：8 组 × 800 case（共 6400 条全幅随机指令）Python/C 字节流完全一致；
修复后 `test_isa_completeness.py` 73/73、difftest 11/11、CSR 13/13、13 个 e2e 全绿。

新增 `trirv_fuzz_mem.py`（访存 + 原子差分 fuzz）：覆盖 ALU fuzz 未涉及的访存语义——
SW/SH/SB 写入与 LW/LB/LBU/LH/LHU 读回的 tryte 序与零扩展、有符号 base + 7-trit
立即数的地址计算（含负/越界地址）、A 扩展 LRW/SCW/AMO* 的保留集与 old-value 返回。
验证：6 组 × 800 case（含 25% 原子序列）Python/C 字节流完全一致，未发现新差异。

新增 `trirv_fuzz_csr.py`（CSR 差分 fuzz）：覆盖 CSRRW/RS/RC 及立即数版的旧值返回、
CSR 地址越界读 0 写忽略、mepc/mtvec 写入 4 对齐。

- **发现的真 bug —— mepc/mtvec 4 对齐前缺模规整**：`CSRRS` 的 `old|src` 是按位或，
  结果可 `≥ 3^45`（如 `4.57e21 > 2.95e21`）。Python `_csr_write` 用 `s(u(val))` 先
  模 `3^45` 再对齐；C `csr_write` 原用 `align_down4(s(val))`，`s()` 对 `≥ MOD_X`
  的值只减一次 `MOD_X`，3 补码规整错误，导致对齐后与 Python 差 1。修法：对齐前先
  `u(val)` 规整——`align_down4(s(u(val)))`，与 Python 一致。非对齐 CSR 写入本就由
  `umod_M(val)` 兜底，不受影响。
- **设计限制（非 bug）**：立即数版 CSR 的 uimm 字段（4 trit，0..80）与 rs1 共用
  `<32` 钳制，uimm≥32 时两版都钳为 0，CSRRWI 无法写入 ≥32 的立即数。两版一致，
  暂不改 ISA 语义。

验证：10 组 × 800 case（共 8000 条 CSR 操作）Python/C 字节流完全一致。

- **P1 落地时发现并修复的真 bug：C VM 解码器字段宽度还是 3 trit。** `decode_one()` 里
  `rd=field(raw,3,5)`、`rs1=field(raw,9,11)`、`rs2=field(raw,13,15)` 是 D3 时期的旧编码；
  ISA 于 9c692fa 恢复 4-trit 字段后漏改这里。后果极隐蔽：寄存器 0..26 的低 3 trit 恰好
  等于自身，**只有 x27..x31（s11、t3..t6）才会解错**——`s11`(27=1000₃) 的低 3 trit 是
  000，解码成 `x0`。首例暴露是 `DIVU s10,s10,s11` 被读成 `DIVU s10,s10,zero`，除零返回
  0，循环一轮就退出。已改为 4-trit。
  教训：差分测试只覆盖程序真正用到的寄存器，**没被用到的编码路径不会自己报错**。

- **C 后端已补齐 struct 按值传参 / sret 返回（2026-11-19）**。约定与 Python 后端一致：
  struct 表达式求值 = 首地址；按值传参 = 调用方传源地址、被调方入口逐字拷进本地副本
  （修改完全隔离）；返回走 sret（调用方在帧内预留缓冲、隐藏 `a0` 传地址、`return`
  逐字拷入后把地址带回去）。sret 占掉 `a0` 后参数窗口是 `a1..a7`，超过 7 个仍走 `t6`
  参数块，块内索引不随 sret 平移。**每个 sret 调用点各占一块独立缓冲**，`f(g(),h())`
  时两块互不覆盖。C 后端覆盖率从 130/148（88%）到 148/148。

- **补 struct 时连带查出一个潜伏的静默错码：`A0_DIRECT` 泄漏。**
  `return f(...)` 为了省掉一次搬运会把结果留在 `a0`（`A0_DIRECT=1`），但这是个**全局标记**，
  实参里的嵌套调用会跟着跳过 `ADDI r, a0, 0`，把寄存器池里失效的旧值当返回值存下来。
  实测修复前 `return f(g(3),g(4))` 返回 **0** 而不是 34，编译期毫无提示。
  修法是进出 `N_CALL` 时保存/恢复该标记，让"直通 a0"只对本层调用生效。
  回归锁在 `trirv_tdd_contract.py` §9。

### 11.3 PC 编址（已实现）

PC 按 **tryte 地址**编址，与 §1「地址按 byte/tryte 编址」一致。指令定长 20 trit = 4 tryte，
故**指令 `i` 的 tryte 地址 = `4*i`**。两套 VM（Python/C）语义完全一致：

| 项 | 语义 |
| --- | --- |
| 取指 | `slot = pc // 4`；`pc < 0`、`pc % 4 != 0` 或越界 → 停机 |
| 顺序执行 | `pc += 4` |
| 分支目标 | `pc = old_pc + 4*sign_extend(imm)`（立即数仍是**指令槽偏移**，保持 ±1093 条跳转范围） |
| `JAL` | 链接地址 `rd = old_pc + 4`；目标 `old_pc + 4*imm` |
| `JALR` | 链接 `rd = old_pc + 4`；目标 `align_down4(rs1 + imm)`（向下对齐到 4，对标 RISC-V 清低位） |
| `AUIPC` | `rd = old_pc + imm*3^7`（基于 tryte PC） |
| `mepc`/`mtvec` | 存 **tryte 地址**，写入时 `align_down4`（4 对齐）；陷入/返回时 `//4` 校验槽范围 |

> 关于 4 对齐：4 不是 3 的幂，无法用位掩码对齐，故用 floor 除法 `addr//4*4`。
> C VM 整数除法向零截断，专门用 `align_down4()` 修正负值，与 Python `//` 一致。
> 立即数单位保持"槽"而非改为"tryte"：若改 tryte 偏移，7-trit B 型跳转范围会从
> ±1093 条缩到 ±273 条；保持槽偏移则工具链（汇编器标签差值、编译器跳转）零改动。

验证：`test_isa_completeness.py` §F 覆盖 JAL 链接、分支、AUIPC、负 JALR 对齐、mepc/mtvec
tryte 保存及 C/Python 差分；`trirv_csr_e2e.py` 13/13 通过（trap 向量按 tryte 地址）。
